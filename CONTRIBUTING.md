## 1. What This Library Is

The **Medhavat Animation Library** is a curated collection of isolated, self-contained animation elements — WebGL scenes, physics simulations, canvas effects, and scroll interactions — built for production-grade use.

**The root `http://localhost:3000/` (the Library Hub) is the front door.** It renders a grid of interactive tiles, one per element. Each tile links to its own standalone experience page.

> **Golden Rule:** Every element must live fully independently in its own folder. The hub connects them. Nothing else should.

## 3. Adding a New Animation Element — Step-by-Step

Follow these steps **in order**. Do not skip any.

### Step 1 — Create the element folder

Use **kebab-case** naming with a meaningful suffix:
- WebGL/Three.js scenes → `*-scene` suffix (e.g., `particle-field-scene`)
- App-like elements with their own logic → `*-app` suffix (e.g., `distortion-app`)
- Simple controllers/utilities → `*-controller` suffix (e.g., `parallax-controller`)

```
my-new-element-scene/
├── index.html
├── README.md
└── src/
    └── app.js
```

### Step 2 — Build the standalone `index.html`

The `index.html` for every element **must** include:

1. A `🏠 Library Hub` back-navigation button in the top-left corner.
2. A proper `<title>` and `<meta name="description">` tag.
3. A link back to `../index.html` for the navigation button.

**Required navigation button pattern (copy this exactly):**

```html
<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8" />
  <meta name="viewport" content="width=device-width, initial-scale=1.0" />
  <title>My Element Title — Medhavat Technologies</title>
  <meta name="description" content="Brief description of what this element does." />
  <style>
    * { margin: 0; padding: 0; box-sizing: border-box; }
    body { background: #05070c; overflow: hidden; }
    #hub-nav {
      position: fixed; top: 1rem; left: 1rem; z-index: 9999;
      display: flex; align-items: center; gap: 0.5rem;
      padding: 0.5rem 1rem; border-radius: 8px; cursor: pointer;
      background: rgba(255,255,255,0.06); border: 1px solid rgba(255,255,255,0.12);
      color: rgba(255,255,255,0.7); font-family: system-ui, sans-serif;
      font-size: 0.8rem; text-decoration: none;
      transition: background 0.2s, color 0.2s;
    }
    #hub-nav:hover { background: rgba(255,255,255,0.12); color: #fff; }
  </style>
</head>
<body>
  <a id="hub-nav" href="../index.html">🏠 Library Hub</a>
  <!-- Your element canvas / container here -->
  <script type="module" src="./src/app.js"></script>
</body>
</html>
```

### Step 3 — Write the `README.md`

Every element must have its own `README.md` at the folder root with at minimum:

- A title and one-paragraph description of what the element does
- **Features & Mechanics** section (list of technical highlights)
- **File Structure** section
- **How to Run** section (both via library hub and standalone)
- **Credits & Acknowledgments** section (if any third-party code, shaders, or inspiration was used — be specific with links)

See [`jellyfish-simulation-app/README.md`](./jellyfish-simulation-app/README.md) as the reference example.

### Step 4 — Register the element in `src/hub.js`

Open [`src/hub.js`](./src/hub.js) and add a new entry to the `ELEMENTS` array. **All fields are required:**

```js
{
  id: 'my-new-element',              // Unique kebab-case ID — matches your folder name (without suffix)
  title: 'My Element Title',         // Human-readable display name for the tile
  icon: '✨',                        // Single emoji icon shown on the tile
  category: 'webgl',                 // Must be one of: 'webgl' | 'canvas' | 'physics' | 'scroll'
  categoryLabel: 'WebGL 3D & Shaders', // Human-readable category badge label
  fps: '60 FPS Native',              // Target frame rate string shown on the tile
  badgeColor: 'rgba(0, 240, 255, 0.2)', // Translucent category badge background colour
  bannerGradient: 'radial-gradient(circle at 50% 50%, #0a1a2e 0%, #05070c 100%)', // Tile banner gradient
  description: 'One to two sentences describing what makes this element unique and how it works.',
  techTags: ['Three.js', 'Tag 2', 'Tag 3'], // 3–5 technology/technique tags
  path: '/my-new-element-scene/',    // URL path — must match the exact folder name
  mathDocs: 'The key formula or algorithm: e.g., Displacement = sin(x * freq + time) * amplitude',
  architecture: [                    // 3–5 bullet points explaining internal architecture
    'First architectural highlight',
    'Second architectural highlight',
    'Third architectural highlight'
  ],
  codeSnippet: `// Minimal usage snippet or run instructions`
}
```

**Category values and their badge colours:**

| Category | Label | `badgeColor` |
|---|---|---|
| `webgl` | `3D WebGL & Shaders` | `rgba(168, 85, 247, 0.2)` |
| `canvas` | `Canvas & Matrix VFX` | `rgba(0, 240, 255, 0.2)` |
| `physics` | `Physics & Spring UI` | `rgba(236, 72, 153, 0.2)` |
| `scroll` | `Scroll Kinetics` | `rgba(34, 197, 94, 0.2)` |

### Step 5 — Register the element in `vite.config.js`

Open [`vite.config.js`](./vite.config.js) and add the new entry to `rollupOptions.input`:

```js
rollupOptions: {
  input: {
    // ... existing entries ...
    myNewElement: resolve(__dirname, 'my-new-element-scene/index.html'), // ← Add this
  }
}
```

**Naming convention for the key:** use camelCase derived from the folder name (e.g., `bloomPortal`, `neuralNetwork`, `myNewElement`).

### Step 6 — Verify everything works

Run the dev server and check both surfaces:

```bash
npm run dev
```

1. Open `http://localhost:3000/` — confirm your new tile appears in the hub grid.
2. Click the tile's **"Launch Experience ↗"** button — confirm it navigates correctly.
3. Click the **"🏠 Library Hub"** button inside your element — confirm it returns to the hub.
4. Click **"Docs / Architecture 📋"** on your tile — confirm the modal shows your description and architecture bullets.
5. Run `npm run build` — confirm it exits with code `0` and your element's HTML is listed in the dist output.

## 4. Folder & File Naming Rules

| What | Rule | Example |
|---|---|---|
| Element folder | `kebab-case` + meaningful suffix | `particle-field-scene` |
| Source files | `camelCase.js` | `particleField.js` |
| HTML entry | Always `index.html` | `my-element/index.html` |
| Shader files | `camelCase.glsl` or `camelCase.js` | `causticShader.js` |
| CSS files | `camelCase.css` | `particleField.css` |
| Vite input key | `camelCase` | `particleField` |
| Hub `id` field | `kebab-case` | `particle-field` |
| Hub `path` field | `/folder-name/` (with trailing slash) | `/particle-field-scene/` |

> **Never** use spaces, underscores, or uppercase letters in folder or file names (except source `.js` files inside `src/`).

## 6. Hub Registration (The Most Critical Step)

> [!IMPORTANT]
> **The hub is the library.** An element that isn't registered in [`src/hub.js`](./src/hub.js) does not exist as far as any user or developer is concerned. This is the single most important step when adding any new element.

The `ELEMENTS` array in `src/hub.js` drives:
- All hub tiles (title, icon, description, links)
- The search system (searches title, description, and techTags)
- The category filter tabs (driven by the `category` field)
- The architecture modal (driven by `architecture` and `mathDocs`)

**Do not create custom HTML tiles in `index.html`.** The hub is fully data-driven. All tile rendering is handled automatically once an entry is added to the `ELEMENTS` array.

## 7. Vite Multi-Page Build Registration

> [!IMPORTANT]
> **If an element's `index.html` is not registered in `vite.config.js`, it will not be included in the production build.**

Every element entry point must be declared under `rollupOptions.input` in [`vite.config.js`](./vite.config.js). The dev server serves the files directly from disk, so missing entries only fail silently at build time — always run `npm run build` to verify.

**The `tslOperatorPlugin` must remain in `plugins` — do not remove it.** It is required by the jellyfish simulation's Three.js TSL shader operator overloading. Removing it breaks the TSL compute kernel compilation.

## 8. Dependency Rules

### Root-level `package.json` is the single source of truth

All dependencies shared across elements (Three.js, Tweakpane, etc.) are installed at the **root level** only. Element folders must **not** have their own `package.json` or `node_modules`.

```bash
# Install a new dependency (from the repo root only)
npm install my-package
```

### Vendored Three.js

The `vendor/three/` directory contains a locally vendored Three.js build. **Do not modify these files.** Import Three.js in element scripts as:

```js
import * as THREE from 'three/webgpu';       // For WebGPU renderer elements
import * as THREE from 'three';              // For standard WebGL elements
import { Fn, uniform, ... } from 'three/tsl'; // For TSL shader nodes
```

> [!WARNING]
> Do not import from `../vendor/three/...` with relative paths in new elements. Always use the `three` package specifier resolved by Vite from `node_modules`. Relative vendor imports are only present in legacy scenes and should not be propagated.

### Keeping Three.js version pinned

The version of `three` in `package.json` is intentionally pinned. The TSL API and `ComputeNode` behaviour have changed frequently across Three.js releases. **Do not upgrade Three.js without testing every WebGPU/TSL element**, particularly `jellyfish-simulation-app`.

## 9. Code Standards

### JavaScript
- **ES Modules only.** All files must use `import`/`export`. No CommonJS (`require`).
- **No TypeScript.** The project is intentionally plain JS for maximum accessibility.
- **No bundler-specific magic comments** (e.g., `/* @vite-ignore */`) unless absolutely necessary and documented with a comment explaining why.
- Use `async/await` over `.then()` chains for readability.
- Prefix internal class methods not meant for external use with `_` (e.g., `_updatePositions`).

### CSS
- Each element that requires styles **must** keep its CSS in its own `src/` folder, not in the root `src/`.
- Do not modify `src/hub.css` or `src/style.css` for element-specific styles.
- Use CSS custom properties (`--variable-name`) for any themeable values.

### Three.js & WebGPU elements
- Always gracefully handle WebGPU unavailability with a WebGL fallback or a user-visible error message.
- Never call renderer backend properties (e.g., `renderer.backend.isWebGPUBackend`) before `await renderer.init()` has completed.
- Use `renderer.computeAsync()` over `renderer.compute()` for all compute shader dispatches.
- Guard any method calls on `ComputeNode` instances (e.g., `updateDispatchCount`) with an existence check, as the Three.js TSL API evolves across minor versions:
  ```js
  if (typeof kernel.updateDispatchCount === 'function') {
    kernel.updateDispatchCount();
  }
  ```

### Performance
- Animation loops must be driven by `renderer.setAnimationLoop()` or `requestAnimationFrame`. Never use `setInterval` for rendering.
- Dispose of geometries, materials, and textures when an element is torn down to prevent GPU memory leaks.

## 10. Intellectual Property, Attribution & Professionalism Policy

> [!IMPORTANT]
> **This policy is non-negotiable and applies to every contributor — human or AI — without exception.**
> Medhavat Technologies maintains the highest standards of professional and legal integrity. Violations of this policy are grounds for immediate reversal of contributions and, if applicable, legal action.

### 10.1 The Core Principle

This library must never contain:
- Code copied verbatim from another project without explicit, verified license permission.
- Assets (images, fonts, datasets, shaders) used without confirming their license allows commercial use.
- Attributions that are vague, inaccurate, or omitted entirely.

**When in doubt — do not include the code or asset. Ask the maintainers first.**

### 10.2 Mandatory Source File Attribution Headers

Every source file (`.js`, `.glsl`, `.ts`) that is derived from, substantially inspired by, or directly incorporates code from any external source **must carry an attribution header comment** at the top of the file. This comment must include:

1. The original author's name and website or GitHub profile.
2. The source repository URL.
3. The license under which the original code was released.
4. A clear description of what was modified by Medhavat Technologies.

**Template:**
```js
/**
 * [Module Name] — [Brief Purpose]
 *
 * Original work by: [Author Name] ([URL])
 * Source:           [Repository or URL]
 * License:          [License Name] © [Year] [Author]
 *
 * Modifications by Medhavat Technologies:
 *  - [Describe change 1]
 *  - [Describe change 2]
 */
```

For fully original code, no external attribution header is required, but a brief authorship note is recommended:
```js
/**
 * [Module Name] — [Brief Purpose]
 * Original work by Medhavat Technologies.
 */
```

### 10.3 Every README Must Have a Credits Section

Every element's `README.md` must include a **Credits & Acknowledgments** section as the final section. This section must:

- Name **every** third-party library used (with URL and license).
- Name **every** external inspiration, concept reference, or design source — even if no code was directly copied.
- Use specific, accurate language to distinguish between:
  - **Direct code use**: _"Includes code from X, used under MIT License."_
  - **Inspired by**: _"Visual concept inspired by X. No code was copied. Full implementation is original."_
  - **Dataset use**: _"Dataset sourced from X, redistributed under PDDL license."_
- Include a plain-language legal note where any ambiguity exists.

**Omitting a Credits section is a blocking error — the contribution must not be merged until it is added.**

### 10.4 Licenses That ARE Acceptable for Use

| License | May use code | May modify | May distribute commercially |
|---|---|---|---|
| MIT | ✅ Yes | ✅ Yes | ✅ Yes (with copyright notice) |
| Apache 2.0 | ✅ Yes | ✅ Yes | ✅ Yes (with NOTICE file) |
| BSD 2/3-Clause | ✅ Yes | ✅ Yes | ✅ Yes (with copyright notice) |
| PDDL / CC0 | ✅ Yes | ✅ Yes | ✅ Yes (no restrictions) |
| ISC | ✅ Yes | ✅ Yes | ✅ Yes (with copyright notice) |

### 10.5 Licenses That Are NOT Acceptable Without Prior Approval

| License | Status | Action Required |
|---|---|---|
| GPL / LGPL / AGPL | ⛔ Not acceptable | Must get maintainer approval — may force open-sourcing |
| CC BY-NC / CC BY-ND | ⛔ Not acceptable | Non-commercial or no-derivatives restrictions conflict with commercial use |
| Proprietary / All Rights Reserved | ⛔ Not acceptable | Cannot be used without a formal written license agreement |
| "No license" (unlicensed repo) | ⛔ Not acceptable | Default copyright law applies — all rights reserved. Do not use. |
| SSPL | ⛔ Not acceptable | Not OSI-approved; commercial distribution restrictions |

> [!CAUTION]
> **Do not assume that publicly available code is free to use.** A GitHub repository without a `LICENSE` file is **not** open source — copyright defaults to the author. Always verify the license before incorporating any external code.

### 10.6 For AI Coding Assistants — Special Instructions

AI coding assistants (GitHub Copilot, Gemini Code Assist, Claude, etc.) working in this repository must:

1. **Never generate code that directly reproduces well-known copyrighted implementations** (e.g., exact Shadertoy shader reproductions) without verifying the source shader's license and adding the required attribution header.
2. **Always check the corresponding README** before modifying a source file to understand what attributions are already documented.
3. **Proactively add attribution comments** when generating code that is based on external techniques, algorithms, or references — even if only conceptually similar.
4. **Refuse to proceed** if asked to copy code from a source whose license is unknown or incompatible. Instead, notify the user and ask for clarification.
5. **Treat all third-party credits as load-bearing** — removing or altering a credit comment or README attribution is strictly forbidden without maintainer approval.

### 10.7 Respectful Attribution Etiquette

Beyond legal compliance, this library upholds a culture of **genuine respect** for the creative work of others in the open-source, shader art, and web development communities:

- Credit authors **by name**, not just by repository URL.
- Use **warm, appreciative language** in credits (e.g., _"with gratitude to"_, _"inspired by the excellent work of"_).
- If a piece of work was genuinely influential or foundational to an element, consider adding a personal note of thanks in the README.
- **Do not minimise or bury attributions** in footnotes or collapsed sections. They belong prominently in the Credits section.

## 11. What NOT to Do

> [!CAUTION]
> Violating these rules will break the library for everyone.

| ❌ Do NOT | ✅ Instead |
|---|---|
| Add element code into `src/hub.js`, `src/hub.css`, or `index.html` | Keep all element code inside the element's own folder |
| Create a new `package.json` inside an element folder | Use the root `package.json` for all dependencies |
| Rename or move existing element folders | Update `vite.config.js`, `src/hub.js`, and the element's `README.md` if a rename is genuinely needed |
| Delete or modify files in `vendor/three/` | Update Three.js via `npm install three@x.x.x` at root |
| Manually edit `public/frame-manifest.json` | It is auto-generated by `scripts/generate-manifest.js` on every `npm run dev` and `npm run build` |
| Add inline `<style>` blocks to the hub's `index.html` | Use `src/hub.css` for hub styles |
| Register an element in `vite.config.js` but not in `src/hub.js` (or vice versa) | Always do both at the same time |
| Use external CDN imports (`<script src="https://...">`) | Install via npm and import as ES module |
| Commit `dist/` or `node_modules/` directories | They are git-ignored — build outputs are never committed |

## 12. Checklist Before Committing

Copy this checklist and confirm every item before pushing a new element:

```
□ Element folder follows kebab-case naming with correct suffix (-scene / -app / -controller)
□ index.html exists in the element root with the hub nav button
□ src/app.js (or equivalent entry) exists inside the src/ subfolder
□ README.md exists with: description, features, algorithm, file structure, how to run, credits
□ Credits section names all original authors, repos, shaders, and datasets with URLs and licenses
□ Legal notes added where any inspiration, concept reference, or dataset was used
□ Source file attribution header comment added to all files derived from external sources
□ All third-party licenses confirmed as compatible (MIT / Apache / BSD / PDDL / ISC)
□ Entry added to ELEMENTS array in src/hub.js with all required fields populated
□ Entry added to rollupOptions.input in vite.config.js
□ npm run dev — tile appears in hub, navigation works both ways
□ npm run build — exits with code 0, element HTML appears in dist output
□ No new package.json created inside the element folder
□ No modifications to src/hub.css, src/hub.js, index.html for element-specific code
□ No modifications to vendor/ directory
```
